# Pass / Fail Record Review — v1.10

Record Review shows **Key** and **Name** in its heading, with **Pass** and **Fail** buttons at the top. Review reasons sit immediately below the heading. The preserved source and live Proposed Hybrid output remain side by side below them, stacking on narrow screens.

The heading uses the selected/mapped source key and retains text such as leading zeros. Standard uploads now recognize common Key Field, Record Key, Key, External Key, Record ID and Reference ID headers for the key suggestion. The mapping screen can override the suggestion. Older records can use their preserved Key/Key Field column; if no selected key has a value, the internal record ID appears. Keys are metadata, not address evidence, and duplicate source keys never merge records.

**Pass** opens a pop-up containing **Initials** only. A reason is neither displayed nor required. **Fail** opens a pop-up requiring **Initials** and **Reason**. Initials are normalized to uppercase and limited to 1–12 characters; a Fail reason must contain text and may be up to 2,000 characters. Confirm records the decision. Cancel or Escape closes only the pop-up and returns to review without saving a decision or losing edits in the open review window.

Pass and Fail are available for pending records and records without a prior human decision, including automatically translated records. Existing completed decisions remain read-only in the UI. The top controls stay outside the scrolling evidence section. Native modal focus handling keeps interaction inside the pop-up and returns focus to review when canceled.

Both decisions save the current structured proposal, including any edits shown in the preview. Original source data remains unchanged. Pass without edits preserves findings and confidence; edited values follow the existing human-supplied-edit behavior. Passing does not waive validation findings or certify address completeness. Fail stores the reason alongside the exact reviewed output. The previous bottom Reviewer/note/Reject/Save edits/Accept form is replaced by these two decisions; edits are committed on Confirm Pass or Confirm Fail.

Each decision is stored as action PASS or FAIL, state PASSED or FAILED, initials, timestamp and the before/after components plus a decision-output snapshot. Pass stores an empty reason; Fail stores the entered reason. Results and audit events save atomically with the record version. Stale/duplicate submissions are rejected. Automatic town approval remains removed.

The existing batch action is now **Pass all pending** and uses the same initials-only pop-up. It applies to all pending records in the batch, including those outside current filters, and retains atomic selection/version checks. It does not apply to already completed decisions. Existing data, old ACCEPT/APPROVE/REJECT/EDIT history and legacy API operations remain supported without rewriting their audit events.

Status filters add **Passed** and **Failed**, including corresponding legacy decisions. Historical filter options remain available. Matching multiple statuses still exports each internal record once. Full analysis adds Review_Decision, Decision_Initials, Decision_At, Decision_Reason and Output_Failed; Review_State records the new values. Existing source/Hybrid output formats and Group/search selection behavior are preserved. Source + Hybrid keeps its concise source-plus-four-lines layout.

IT/API: PATCH /api/records/{id} accepts action PASS with initials and version, omitting reason; FAIL requires initials, reason and version. Optional edits are validated and included in the decision. Nonempty reasons on PASS are rejected. Existing same-origin protection, completed-job guard and optimistic concurrency checks remain. POST /api/batches/{id}/accept supports action PASS, initials and the explicit versioned selection. Legacy requests still use their existing reviewer/reason contract. No destructive schema migration or dependency change is required.
